Task: Implement NASSAQ Enterprise Form UX Pattern across the system

Objective:
Build a unified, reusable, production-safe Form UX system for all major forms and wizards in NASSAQ.

This is a system-level UX architecture task, not a one-page visual improvement.

Primary Goal:
Standardize all major forms so they are clearer, more structured, easier to complete, and consistent across the platform.

--------------------------------------------------
1) CORE UX REQUIREMENTS
--------------------------------------------------

The form system must follow these rules:

1. No vertical scroll on desktop forms/wizard steps
2. Multi-step forms must use a clear stepper
3. Each step should fit within the viewport as much as possible
4. Use grid layout (2–3 columns on desktop where appropriate)
5. Group fields into logical sections/cards
6. Sticky action bar must always remain visible
7. Validation must happen per step
8. No data loss between steps
9. Clear, premium, structured UI
10. Errors must be visible without requiring scroll

--------------------------------------------------
2) REUSABLE COMPONENTS TO BUILD
--------------------------------------------------

Create reusable components first, before page-by-page refactoring:

- FormContainer
- FormStep
- FormSection
- FormGrid
- StickyActionBar
- StepIndicator
- ValidationMessage
- Optional: FormHeader / FormStepLayout

These components must be reusable across the platform and not hardcoded for one screen.

--------------------------------------------------
3) IMPLEMENTATION SCOPE
--------------------------------------------------

Apply this pattern first to these flows only:

Phase 1:
1. Create School flow
2. Teacher Registration
3. Student Creation

Do not refactor the entire platform blindly.
Start with these flows and establish the reusable pattern properly.

--------------------------------------------------
4) STRICT IMPLEMENTATION RULES
--------------------------------------------------

Important:
- Do not break existing backend integration
- Do not break form submission logic
- Do not break validation rules
- Do not cause state loss between steps
- Do not make cosmetic-only changes
- Do not implement duplicated layout logic per page
- Build shared components and then apply them

--------------------------------------------------
5) LAYOUT RULES
--------------------------------------------------

Desktop:
- Zero vertical scroll is the target
- Each step must keep all required fields and action buttons visible
- Use multi-column layout where appropriate

Tablet:
- Minimize scroll as much as possible

Mobile:
- Prioritize usability and readability
- Scroll may exist if necessary, but structure must remain clear

If a step is too dense:
- split it into smaller logical steps
- do not compress fields excessively

--------------------------------------------------
6) FORM DESIGN RULES
--------------------------------------------------

Each form step should include:
- clear title
- optional short description
- grouped inputs
- visible validation
- sticky action bar

Each step should ideally contain only a manageable number of fields.
If a step has too many fields, restructure it.

--------------------------------------------------
7) ACCEPTANCE CRITERIA
--------------------------------------------------

The implementation is only considered complete if:

1. Desktop school creation flow has no vertical scroll
2. Action buttons are always visible
3. Back/Next navigation does not lose data
4. Validation errors are visible within the same step
5. Teacher Registration follows the same pattern
6. Student Creation follows the same pattern
7. Shared reusable form components are actually used
8. UX is visibly more structured, consistent, and professional

--------------------------------------------------
8) OUTPUT REQUIRED
--------------------------------------------------

Before coding:
Provide:
1. component architecture
2. pages/flows to be updated
3. step restructuring plan
4. layout strategy

After coding:
Provide:
1. exact files/components created or modified
2. how scroll was eliminated
3. which steps were split or redesigned
4. confirmation of no data loss
5. confirmation of desktop no-scroll behavior
6. any trade-offs made for mobile/tablet

--------------------------------------------------
9) EXECUTION ORDER
--------------------------------------------------

Implement in this order:
1. Build reusable components
2. Build shared layout rules
3. Apply to Create School
4. Apply to Teacher Registration
5. Apply to Student Creation
6. Test state persistence and validation
7. Report final results
