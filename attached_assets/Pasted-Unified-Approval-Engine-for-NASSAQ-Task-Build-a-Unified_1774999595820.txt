Unified Approval Engine for NASSAQ

Task: Build a Unified Approval Engine for NASSAQ

Objective:
Design and implement a reusable, scalable, production-grade Unified Approval Engine for NASSAQ to manage all approval-based onboarding and activation workflows through one centralized system.

This is not a simple feature.
This must be an approval architecture and engine that becomes the standard governance layer for all future approval-required entities in the platform.

System Context:
NASSAQ is a multi-tenant school management platform with:
- Platform Admin governance
- strict RBAC
- tenant-aware architecture
- school-based isolation
- multiple user/entity types
- public registration flows
- admin-side activation and approval workflows

The approval engine must unify all approval-related flows under one system instead of handling each case separately with fragmented logic.

--------------------------------------------------
1) CORE BUSINESS GOAL
--------------------------------------------------

The system must ensure that any entity requiring review before activation is first stored as a request in a centralized approval workflow, then reviewed by the authorized approver, then either:
- approved and activated
- rejected
- marked under review
- returned for revision if this state is supported

The engine must prevent invisible requests, partial activation, inconsistent entity creation, and uncontrolled onboarding.

--------------------------------------------------
2) ENGINE SCOPE
--------------------------------------------------

The Unified Approval Engine must support, at minimum, these approval types:

Phase 1 required:
1. School registration requests
2. Independent teacher registration requests

Architecture must be designed to support future approval types such as:
3. School staff account requests
4. Parent account requests
5. External partner requests
6. Teacher invitation acceptance approvals
7. Account upgrade requests
8. Entity change requests
9. Sensitive profile update approvals
10. Any future workflow requiring authorization before activation

Do NOT hardcode the engine for schools only.
Build a reusable approval engine.

--------------------------------------------------
3) FUNDAMENTAL SYSTEM RULE
--------------------------------------------------

Pending Request != Active Entity

This distinction must be explicit and enforced in:
1. database design
2. backend workflow
3. admin UI
4. lifecycle logic
5. RBAC/tenant activation logic

Examples:
- A school registration request is not yet an active school tenant
- An independent teacher registration request is not yet an active teacher account with full permissions
- Approval is the step that transforms a request into a usable active entity

--------------------------------------------------
4) APPROVAL ENGINE RESPONSIBILITIES
--------------------------------------------------

The Unified Approval Engine must handle:

1. Request intake
2. Request classification by type
3. Request validation
4. Request persistence in unified database
5. Lifecycle state management
6. Review queue management
7. Approval / rejection / under review actions
8. Downstream activation logic
9. Traceability and auditability
10. Admin visibility and filtering
11. Safety against partial activation
12. Extensibility for future approval types

--------------------------------------------------
5) REQUIRED LIFECYCLE STATES
--------------------------------------------------

Implement a clear standardized lifecycle.

Minimum required statuses:
- pending_approval
- under_review
- approved
- rejected

Optional but recommended:
- draft
- cancelled
- archived
- requires_revision

Rules:
- Every request must have one explicit status
- Status transitions must be controlled, validated, and logged
- Invalid transitions must be blocked

Example valid transitions:
- pending_approval -> under_review
- pending_approval -> approved
- pending_approval -> rejected
- under_review -> approved
- under_review -> rejected
- approved -> archived
- rejected -> archived

--------------------------------------------------
6) UNIFIED DATA MODEL REQUIREMENTS
--------------------------------------------------

Build a centralized approval request model.

Preferred architecture:
Create a generic ApprovalRequest model/table/collection that can support multiple request types.

Suggested structure:

ApprovalRequest:
- id
- request_type
- title
- applicant_type
- applicant_name
- applicant_email
- applicant_phone
- source
- status
- submitted_at
- reviewed_at
- reviewed_by
- review_notes
- rejection_reason
- linked_entity_type
- linked_entity_id
- linked_user_id
- linked_school_id
- tenant_id
- priority
- payload_snapshot
- normalized_payload
- metadata
- created_at
- updated_at

Required fields explanation:
- request_type:
  e.g. school_registration, independent_teacher_registration
- source:
  e.g. public_signup, admin_created, invitation_flow
- payload_snapshot:
  raw or semi-raw submission for traceability
- normalized_payload:
  clean normalized structure used for processing
- linked_entity_id:
  populated after approval if active entity is created
- tenant_id:
  null until approval if tenant is not yet active, unless draft tenant architecture is intentionally used

Important:
If you prefer separate request collections/tables per request type, that is acceptable only if:
- all approval logic remains unified
- all requests can still be queried consistently
- lifecycle model remains standardized
- platform admin queue remains centralized

--------------------------------------------------
7) PHASE 1 APPROVAL TYPES
--------------------------------------------------

A) School Registration Request
When a school registers through public "تسجيل جديد":
- create ApprovalRequest of type school_registration
- set status to pending_approval
- save all relevant school + principal submission details
- make request visible in Platform Admin queue
- do NOT fully activate the school until approval
- approval must trigger school activation workflow

B) Independent Teacher Registration Request
When an independent teacher registers through public "تسجيل جديد":
- create ApprovalRequest of type independent_teacher_registration
- set status to pending_approval
- save teacher details
- make request visible in Platform Admin queue
- do NOT fully activate teacher account for operational use until approval
- approval must trigger teacher activation workflow

--------------------------------------------------
8) APPROVAL ACTION BEHAVIOR
--------------------------------------------------

The engine must support these actions:

1. approveRequest(requestId, reviewer, notes)
2. rejectRequest(requestId, reviewer, reason)
3. markUnderReview(requestId, reviewer, notes)
4. archiveRequest(requestId, reviewer)
5. getApprovalQueue(filters)
6. getRequestDetails(requestId)
7. validateTransition(currentStatus, targetStatus)

All approval actions must be centralized in the engine, not duplicated in scattered modules.

--------------------------------------------------
9) APPROVAL EXECUTION LOGIC
--------------------------------------------------

Approval must safely execute downstream logic depending on request_type.

A) For school_registration approval:
The engine must:
- validate request integrity
- create or finalize school entity
- create or finalize tenant / SchoolId
- create or activate principal user
- link principal to school
- link school to tenant
- assign appropriate status to school
- store linked entity references back on ApprovalRequest
- mark request as approved
- ensure school becomes visible in appropriate admin pages

B) For independent_teacher_registration approval:
The engine must:
- validate request integrity
- create or activate teacher user
- assign correct role
- attach correct access model
- store linked user/entity references back on ApprovalRequest
- mark request as approved

C) On rejection:
- request status becomes rejected
- reviewed_by, reviewed_at, notes saved
- no active entity should be created unless your architecture intentionally pre-created draft entities
- historical trace must remain

--------------------------------------------------
10) TRANSACTION / CONSISTENCY REQUIREMENTS
--------------------------------------------------

The engine must be safe against partial completion.

Requirements:
- approval actions must be atomic or transaction-safe as much as current stack allows
- if activation fails midway, request must not be incorrectly marked approved
- prevent orphan entities
- prevent partially activated tenant/user/school relationships
- write logs for failure steps
- store clear error reason when activation fails

For critical flows, add post-approval verification:
Example:
After school approval:
- verify school exists
- verify school linked to tenant
- verify principal linked to school
- verify request marked approved
- verify admin list visibility works

--------------------------------------------------
11) RBAC AND AUTHORIZATION RULES
--------------------------------------------------

Only authorized roles may act on approval requests.

Required:
- Platform Admin can review school and independent teacher requests
- future approval types can define their own approver roles

Implement explicit permission layer:
- who can view which request types
- who can approve/reject which request types
- who can only read but not act

All approval actions must be logged with:
- reviewer user id
- role
- timestamp
- action
- request id
- notes/reason if applicable

13) PUBLIC REGISTRATION FLOW REQUIREMENTS
--------------------------------------------------

Public registration must integrate with the engine properly.

When the user submits registration:
- create ApprovalRequest
- return structured success response
- show user-friendly message:
  request submitted successfully and awaiting review
- do not pretend that account is fully active if approval is still pending

System must clearly distinguish between:
- request received
- request approved
- account active

--------------------------------------------------
14) UNIFIED DATABASE PRINCIPLES
--------------------------------------------------

The unified database must behave as follows:

1. Single source of truth for all approval requests
2. Every request stored centrally
3. Every request queryable by:
   - type
   - status
   - source
   - date
   - reviewer
4. Every request has full lifecycle trace
5. Every approved request maps cleanly to active entity or user
6. Every rejected request remains historically visible
7. Every review action is traceable
8. No invisible pending requests
9. No frontend-only approval states
10. No activation outside governed engine logic for approval-based flows

15) ENGINE EXTENSIBILITY REQUIREMENTS
--------------------------------------------------

Design the engine so new request types can be added with minimal effort.

Preferred extensibility pattern:
- generic ApprovalRequest model
- request type enum/config
- approval handler registry by request type
- shared status transition engine
- shared reviewer action service
- shared listing/filter service

Recommended architecture:
- approval engine core service
- approval request repository
- request type handlers
- approval action service
- admin queue API
- approval audit service

Example:

  school_registration: handleSchoolRegistrationApproval,
  independent_teacher_registration: handleIndependentTeacherApproval,
  ...
}

--------------------------------------------------
22) CRITICAL REQUIREMENTS
--------------------------------------------------

- Do NOT build a school-only special case
- Do NOT fake approval through UI-only status changes
- Do NOT allow pending requests to become invisible
- Do NOT mix pending requests and active entities carelessly
- Do NOT mark requests approved before full activation succeeds
- Do NOT scatter approval logic across unrelated modules
- Build this as a true engine and governance layer
- The final solution must be reusable, scalable, traceable, and production-safe

















Implementation Priority for Unified Approval Engine:

Build the Unified Approval Engine in this order:

Phase 1:
1. ApprovalRequest data model / repository
2. Standard status lifecycle and transition rules
3. Generic approval service
4. Handler for school_registration
5. Handler for independent_teacher_registration
6. Platform Admin queue APIs
7. Platform Admin UI tabs:
   - طلبات المدارس
   - طلبات المعلمين المستقلين
8. Approve / reject / under review actions
9. Logging + audit integration
10. Apply to public "تسجيل جديد" flow

Phase 2:
- Add "All Requests" consolidated queue
- Add filtering, search, sorting
- Add request details drawer/modal
- Add migration/normalization for old records
- Add handler registry for future approval types

Important:
Start with school and independent teacher approvals first, but architect the engine as reusable from day one.
