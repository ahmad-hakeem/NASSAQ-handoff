
بعد المراحل السابقة أصبح نظام **NASSAQ** يمتلك:

* بنية تشغيلية مستقرة
* Session Engine يعمل فعليًا داخل Teacher Module
* تدفق بيانات حقيقي بين Teacher → Student → Parent
* Multi-Tenant Isolation
* RBAC يعمل
* Audit Logs فعالة
* AI Insights عبر Hakim AI
* Reporting Engine
* Export System
* Role Switching

الآن نبدأ **المرحلة الثامنة** والتي تهدف إلى:

**تحويل النظام من بيئة تطوير إلى نظام جاهز للتشغيل الإنتاجي واسع النطاق.**

هذه المرحلة تركز على:

* الاستقرار
* الأداء
* الأمان
* قابلية التوسع
* الصيانة طويلة المدى

مهم جدًا:

لا تقم بإعادة بناء النظام من الصفر.
ولا تغيّر المعمارية الأساسية بدون ضرورة واضحة.

# أولًا — Server Modularization

من تقارير المراحل السابقة:

```text
server.py > 16,000 lines
```

هذا يجعل الصيانة صعبة ويزيد احتمال الأخطاء.

لكن لا نريد إعادة كتابة النظام بالكامل.

---

## المطلوب

إعادة تنظيم backend تدريجيًا عبر تقسيم `server.py` إلى وحدات واضحة.

يفضل الهيكل التالي:

```
backend/
   routes/
       auth_routes.py
       school_routes.py
       teacher_routes.py
       student_routes.py
       parent_routes.py
       session_routes.py
       reporting_routes.py
       analytics_routes.py
       integration_routes.py

   services/
       auth_service.py
       session_service.py
       reporting_service.py
       notification_service.py

   engines/
       smart_scheduling_engine.py
       hakim_ai_engine.py
       reporting_engine.py

   middleware/
       tenant_enforcement.py
       auth_middleware.py
       audit_middleware.py
```

---

## قواعد مهمة

* لا تغيّر أسماء APIs الحالية
* لا تكسر routes الموجودة
* استخدم include_router فقط
* حافظ على backward compatibility

# ثانيًا — Performance Optimization

بعد توسع النظام، يجب تحسين الأداء.

---

## المطلوب

تحليل نقاط الأداء الحرجة مثل:

* queries الثقيلة
* aggregation pipelines
* session queries
* timetable queries
* reporting queries

---

## تحسينات مطلوبة

### 1. Database Indexing

تأكد من وجود indexes على:

```
school_id
user_id
teacher_id
student_id
session_id
class_id
date
```

---

### 2. Query Optimization

راجع:

* timetable_sessions queries
* attendance queries
* reporting aggregation

وتأكد من أنها لا تقوم بعمليات غير ضرورية.

---

### 3. API Response Optimization

* إزالة البيانات غير المستخدمة
* تقليل payload size
* تحسين pagination

---

### 4. Caching (إذا كان مناسبًا)

يمكن استخدام caching محدود للبيانات التي لا تتغير بسرعة مثل:

* official curriculum
* school settings
* static configuration

---

# ثالثًا — Security Hardening

الأمان عنصر أساسي قبل التشغيل الإنتاجي.

---

## المطلوب

مراجعة النظام بالكامل من ناحية الأمان.

---

## عناصر الأمان المطلوبة

### 1. Authentication Security

تأكد من:

* JWT validation
* expiration
* refresh strategy
* secure token handling

---

### 2. Role-Based Access Control

راجع:

* كل endpoint
* allowed roles
* tenant validation

وتأكد أنه لا يوجد endpoint يسمح بتجاوز الصلاحيات.

---

### 3. Tenant Isolation

تحقق أن كل query مرتبطة بـ:

```
school_id
```

ولا يمكن لمستخدم الوصول إلى بيانات مدرسة أخرى.

---

### 4. Input Validation

راجع جميع endpoints للتأكد من:

* validation
* sanitization
* منع injection

---

### 5. Rate Limiting

إضافة rate limiting على:

* login
* critical endpoints
* export operations

---

* environment variables
