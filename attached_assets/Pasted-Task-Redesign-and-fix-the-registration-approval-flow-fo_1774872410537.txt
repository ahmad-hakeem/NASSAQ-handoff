Task: Redesign and fix the registration approval flow for new Schools and Independent Teachers in NASSAQ, and enforce correct unified database behavior

Severity: HIGH
This affects platform governance, onboarding logic, user approval workflow, and data consistency.

Problem Statement:
Currently, any new registration coming from:
1) a new School
2) an Independent Teacher

must automatically appear inside the Platform Admin account for review and approval.

This behavior is currently missing / incomplete / inconsistent and must be implemented and fixed properly.

Required Product Behavior:
Any new registration through the public "تسجيل جديد" flow must NOT disappear or remain outside Platform Admin visibility.

Instead, it must automatically appear in Platform Admin under "إدارة المستخدمين" inside a NEW dedicated tab structure.

--------------------------------------------------
1) REQUIRED UI CHANGE IN PLATFORM ADMIN
--------------------------------------------------

In Platform Admin → page "إدارة المستخدمين"

Add a new tab next to the existing tabs:
- مستخدمين
- مستخدمو المدارس
- طلبات المعلمين المستقلين

Add a NEW tab:
- طلبات المدارس

This new tab must show all newly registered schools that are waiting for review/approval by Platform Admin.

Final required tabs:
1. مستخدمين
2. مستخدمو المدارس
3. طلبات المعلمين المستقلين
4. طلبات المدارس

Meaning of each tab:
- مستخدمين:
  General system/platform users as per current logic
- مستخدمو المدارس:
  Users already associated with approved/active schools
- طلبات المعلمين المستقلين:
  New independent teacher registration requests awaiting approval
- طلبات المدارس:
  New school registration requests awaiting approval

  Platform Admin → إدارة المستخدمين → طلبات المعلمين المستقلين

--------------------------------------------------
3) CRITICAL SYSTEM RULE
--------------------------------------------------

NO new registration should bypass the unified database.
NO new registration should exist only in frontend state.
NO new registration should be invisible to Platform Admin.

Every registration must be written immediately and consistently into the centralized unified database with the correct entity relationships and approval status.

--------------------------------------------------
4) REQUIRED UNIFIED DATABASE BEHAVIOR
--------------------------------------------------

You must define and enforce the correct system behavior for storing ALL registration requests inside the unified database.

The system must behave as follows:

A) Single Source of Truth
The database must be the single source of truth for:
- school registration requests
- independent teacher registration requests
- principal accounts
- school entities
- approval statuses
- role assignment readiness
- tenant readiness / activation state

B) On registration submission, the system must persist data immediately
When any registration form is submitted successfully:
- data must be stored immediately in DB
- request must get a unique ID
- request must get a type
- request must get a status
- request must get timestamps
- request must become visible in the correct Platform Admin approval tab

C) No hidden temporary logic
Do not rely on:
- temporary frontend cache
- only local component state
- only session state
- incomplete draft objects without DB persistence
unless explicitly intended as draft mode

D) Status-driven workflow
Each registration request must have an explicit lifecycle state.

Recommended statuses:
- pending_approval
- under_review
- approved
- rejected
- archived (optional)

E) Clear entity separation
The system must distinguish clearly between:
1. registration request record
2. actual approved system entity

Example:
- A school registration request is not yet the same as a fully active approved school tenant
- An independent teacher request is not yet the same as an active approved teacher account with full permissions

This distinction is essential.

6) APPROVAL ACTION BEHAVIOR
--------------------------------------------------

A) When Platform Admin approves a school request:
The system must do all required activation logic safely:
- create or finalize school entity
- create or finalize tenant / SchoolId
- create or activate principal user
- link principal to school
- move request status to approved
- ensure school appears in correct admin school views
- ensure approved users move into the correct user lists

B) When Platform Admin rejects a school request:
- request status becomes rejected
- review metadata saved
- no active school tenant should be created unless architecture intentionally pre-created draft entities
- rejected request must remain traceable historically

C) When Platform Admin approves an independent teacher request:
- create or activate teacher user account
- assign correct role
- status becomes approved
- ensure visibility in correct user management views

D) When Platform Admin rejects an independent teacher request:
- request status becomes rejected
- save reviewed_by, reviewed_at, notes
- keep historical trace

--------------------------------------------------

The unified database must follow these rules:

1. Every new registration is recorded centrally
2. Every request has unique identity and lifecycle state
3. Every approval action is traceable
4. No data duplication without purpose
5. No mixing between pending requests and active production entities unless explicitly modeled

7. Every rejected request must remain historically visible for audit and admin review
